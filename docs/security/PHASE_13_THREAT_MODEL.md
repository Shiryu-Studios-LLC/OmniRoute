# Phase 13 Security Threat Model

**Review status:** source review of the current Phase 3–15 implementation slices; Phase 13 exit is **not met**. This document records controls that are visible in source and the remaining attack paths. It is not a deployment or penetration-test report.

## Scope and trust boundaries

This review covers tenant context and SQLite access, API-key membership roles, compliance audit access, the remote MCP registry/discovery path, local-agent enrollment and heartbeats, the Cloudflare connector device channel, and the Worker/D1 API. The Worker exposes privileged server-to-server tenant/provider/device CRUD, device-authenticated connect/heartbeat/poll/result routes, and a customer API-key-authenticated local capability invocation route. Customer keys are issued by a platform administrator; independent owner verification and live Cloudflare deployment validation are not implemented.

| **High, deployment blocker**          | A leaked or misrouted Worker admin token grants cross-tenant CRUD and credential-management authority.                                            | All `/__cloud/v1/tenants/{tenantId}` operations authorize against one global configured Worker token; tenant ID comes from the URL and is not bound to a customer principal. This is a privileged control-plane API, so its safety depends on the token remaining server-side and only trusted services being able to call it. Admin mutations append operation audit events, but that does not mitigate compromise of the shared token. No per-tenant caller authorization or token-rotation mechanism is present. | **High, incomplete feature boundary** | Customer API-key holders can invoke local capabilities, but customer ownership is not independently verified and deployed behavior is unverified. | The Worker now has D1-backed device enrollment/revocation plus device-authenticated connect, heartbeat, poll, and result routes, and a per-device Durable Object binding. | **Medium** | Provider credential ciphertext is accepted based on envelope shape alone. | The Cloud API verifies the `enc:v1` string format before storing credentials and redacts those fields on reads, but the API layer does not authenticate/decrypt the envelope or bind it to a tenant/key version. ## Closed findings in this worktree

- Customer gateway invocations now require a validated `Idempotency-Key`; a tenant-scoped D1 claim binds tenant, principal, API key, device, capability, and canonical payload, then replays bounded completed responses under the same request ID. Expired leases can be claimed for retry, while active duplicates and changed operations conflict. Focused tests cover replay, tenant separation, conflicts, and preflight recovery. This is source and local-D1-double evidence; deployed D1/DO semantics remain unverified.
- Provider quota state, reasoning-cache records and process entries, quota-pool consumption logs, and global semantic-cache/fallback administration now have tenant or platform-admin boundaries. Migrations 182/183 preserve legacy rows under the platform tenant; focused cross-tenant and migration tests cover the new boundaries.
- Shared semantic-cache invalidation, cache statistics/memory clearing, fallback-policy administration, and global cache configuration are restricted to the platform-admin tenant. The JSON settings export already verifies the key-derived tenant and rejects customer keys; route tests cover that denial.
- Per-connection rate-limit controls (including the deprecated alias) and global search statistics are now restricted to the platform-admin tenant; customer management keys are denied before connection state or recent query history is read or changed.
- Chat idempotency response keys now include authenticated tenant and API-key principal identity, preventing one customer or API key from replaying another key's cached response. A behavioral test stores one tenant's response, verifies its retry hits, and verifies another tenant/key misses.
- Customer tenant provisioning now binds the initial verified owner's role to the generated API-key principal used by request authorization. Tenant role enforcement also covers quota and usage management routes, so a member with broad API-key scopes retains read-only access on those resources. Focused provisioning and role-policy tests pass.
- Front Desk now parses quoted `.env` values and limits public chat requests per tenant and socket peer (30 per minute by default). The counter is process-local; multi-instance deployments must enforce limits at the gateway.
- Local-agent inventory, registration, and revocation now participate in tenant role checks; focused policy tests cover read/manage permissions. Successful registration and revocation emit tenant-scoped audit rows without the device credential. Heartbeats emit a safe audit event when status or capabilities change; the API test checks the transition details contain no credential or signature and that unchanged heartbeats are not logged again.
- SQLite compliance audit rows now store tenant ownership and `getAuditLog()`/`countAuditLog()` constrain every query to the current tenant. A route regression test verifies tenant A cannot read tenant B's audit event.
- Compliance audit write failures keep the product request resilient while incrementing a process-local failure counter and emitting a fixed error log with no request, tenant, or database details. A regression test verifies a failed write increments the counter. This is an operational signal, not durable audit evidence.
- Shared community federation server settings are restricted to the platform tenant; customer management keys cannot read or mutate this instance-wide configuration. A route contract test covers GET, POST, and DELETE authorization ordering.
- Conversation roots, transcript turn nodes, call-log artifact lookup, and detailed request bodies now carry tenant ownership. A/B tests cover shared external session IDs and call-log IDs, detail lookups/counts, and tenant-specific retention/purge; migration 173 backfills legacy detailed logs to the platform tenant.

## Test evidence and limits

The current unit suite contains focused cases for tenant provider/API-key isolation, role checks, audit context, MCP endpoint validation/SSRF defenses, signed heartbeat replay and revocation, connector-gateway lease/revocation primitives, customer-key lifecycle, invocation authorization, D1 helper isolation, and rejection of customer management keys from shared cache, rate-limit, and search-stat surfaces. Representative files are [`multi-tenant-provider-isolation.test.ts`](../../tests/unit/multi-tenant-provider-isolation.test.ts#L37), [`tenant-permissions.test.ts`](../../tests/unit/authz/tenant-permissions.test.ts#L98), [`tenant-remote-mcp-runtime.test.ts`](../../tests/unit/tenant-remote-mcp-runtime.test.ts#L60), [`local-agents-api.test.ts`](../../tests/unit/local-agents-api.test.ts#L69), [`connector-gateway.test.ts`](../../tests/unit/connector-gateway.test.ts#L54), [`cloud-customer-identity.test.ts`](../../tests/unit/cloud-customer-identity.test.ts#L93), [`cloud-gateway-http-api.test.ts`](../../tests/unit/cloud-gateway-http-api.test.ts#L525), [`cloud-usage-audit-rate-limit.test.ts`](../../tests/unit/cloud-usage-audit-rate-limit.test.ts#L201), and [`platform-admin-policy-routes.test.ts`](../../tests/unit/platform-admin-policy-routes.test.ts).

These tests exercise local adapters and in-memory D1 doubles. They do not demonstrate production tenant identity binding, owner verification, D1 migration deployment, Worker secret isolation, Cloudflare controlled egress (which is not wired), deployed Node egress behavior against an external MCP server, Durable Object atomicity or end-to-end connector transport. Unit tests prove that the Node transport pins its resolver callback to the validated address set; they are not a production egress test. No production/staging deployment was reviewed as part of this source-based threat model.

## Phase 13 exit decision

**Do not mark Phase 13 complete.** Remaining blockers include the global privileged Cloud API, Worker controlled MCP egress wiring, missing customer inference usage accounting, independent customer-owner verification, Front Desk integration, and live staging validation. Customer API-key local capability invocation now has durable idempotency at the source level, but its deployed D1/DO behavior is unverified. Re-run the targeted security suite after each of those boundaries changes.
